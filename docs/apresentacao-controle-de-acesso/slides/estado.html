O que falta para produção

Decisão: política no cliente

  • O backend GraphQL não muda: segue com a chave única, guardada só no servidor do app
  • Cada app define as próprias regras no seu acl.yml
  • Limite aceito: o dado negado chega ao app antes de ser removido

A implementar

  1. Trocar o dev-login pelo gateway real: o app só valida o JWT
  2. Ler o papel da tabela user_role no banco, não do acl.yml
  3. Definir com o negócio os papéis e as regras de cada app e conferi-las com os dados reais
  4. Cobrir os outros caminhos de dados: o modo sql não passa pela política
Decisão: as restrições são de cada app, então a política continua no cliente (neste app) e o servidor GraphQL não muda. O custo é que o dado negado trafega até o app e é removido ali; por isso a api_key única fica só no servidor do app e nunca vai ao front. Itens a implementar: (1) o dev-login é só da POC; em produção o token vem do gateway e o app valida com o mesmo AUTH_SECRET. (2) Hoje users: no acl.yml faz o papel da tabela user_role. (3) Os papéis de exemplo usam as colunas do dominio.md do pack New Age e não foram conferidos contra os dados reais. (4) A política hoje só é aplicada em graphql_config (reportTable, reportAggregate e reportSchema); o modo sql (db_config.run_select) não passa por ela.
